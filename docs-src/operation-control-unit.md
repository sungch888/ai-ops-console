## 0. 结论先行

**建议能力单元名称**：操作控制单元（页面建议叫「资源操作控制台」，代码/文档内部编号前缀 `OC-`）。

**一句话定位**：把「已被批准的决策」变成「对资源的真实变更」的那一层——统一承接部署、发 Key、调配额、分配训练资源、发布/上下架、扩缩容、隔离恢复等**写操作**，强制做到**有单才执行、有权限才执行、执行有归属、结果有验证、失败有回退、全程有留痕**。

**三条不可动摇的设计基调（均来自原文）**

1. **工单是唯一执行通道**：任何实际变更（人或系统执行）必须先有覆盖本次「审批 + 执行 + 验证」的工单，不得绕过工单直接改（原文 1.1-8）。范围明确包含账号角色指定、权限开关、平台配置、模型及资源变更。**无覆盖工单 → 硬阻断**。
2. **面板只读、不做执行入口**：面板不新增自动动作、不因查看默认开放修改配置、不虚构阈值或自动放宽限制（原文 GW-12、5.1-6、5.6、MS-02、SP-04）。所有写入口收敛在工单/操作侧。
3. **自动执行必须有「策略授权边界」**：获批策略范围内自动执行、不逐次等人工审批；**超范围转人工审批；未获批不得执行**；自动扩缩容**每次执行前先建变更工单，建单失败不得执行**（原文 1.1-9、2.8-4）。这是原文唯一成型的自动化范式，本单元把它抽象为通用自动执行语义。

**与现有原型的关系**：不是再加一个孤立页面，而是把现在散在 3 个地方的写路径**收敛成一层可复用、可审计、可扩展的执行内核**。

## 1. 为什么要单独成一个能力单元（问题定义）

现有原型的写路径已经存在，但割裂：

| 现有入口 | 覆盖的写操作 | 实现要点 | 问题 |
| --- | --- | --- | --- |
| `/ops/workflow` 资源调配工作台 | 16 种工单类型（扩容/回收/抢占/副本/权重/凭证发放/回收/配额/处置/模型回退/下线/接入阻断恢复/模型部署/训练预留/训练释放） | 提交即准入预检 → 审批 → 排队/变更窗口 → 执行 → 生效验证 → 回收；`model_deploy` 走「下发外部执行 + 回执才生效」 | 工单类型是枚举硬编码；状态词一套；**无双人复核**；无策略授权边界 |
| `/ops/apply` 申请与审批台 | 申请 Key、申请训练算例、归还 | 准入校验拒绝原因回显；审批来源可外部回写、超时人工接管 | 与工作台**同一类动作两套受理口径**；Key 发放执行链路缺失 |
| `/ops/commands` 处置指令台 | 限流/暂停/隔离/禁用等运行处置 | **dry-run 预计算影响面 → 二次确认下发 → 设备确认 → 失败/超时转人工兜底 → 反向指令回滚**；权限三档（看事件 / 日常下发 / 紧急下发）；回写幂等 | 这套框架最完整，但**只服务安全处置**，没有对外泛化为通用操作框架 |

由此产生的具体后果：

1. **动作口径不一致**：同样是「调整配额」，工作台里是工单 `quota_adjust`（还进了紧急通道），审批台里是 Key 申请附属，处置台里没有；用户不知道去哪个入口、走哪套审批。
2. **权限判定分散**：`PermKey` 只到「模块 view/manage」粒度（`src/engine/auth.ts:14`），无法表达「能提交 Key 申请 / 能执行发 Key / 能复核 / 能改配额上限 / 能看原文」这类原文要求的逐账号细粒度差异（原文 1.3）。
3. **强制规则没有被统一执行**：原文对凭证类动作要求「一人执行、另一名不同账号复核，未复核不得标记发放成功」（2.6-3），全仓无任何建模；部署「实例健康 + 网关注册/路由生效 + 经网关试调用」三段成功判定（2.5-2）也没有落点。
4. **写操作缺「自动执行」的合法通道**：自动扩缩容、到期回收、异常隔离在原文里都是"平台自动执行 + 执行前建单 + 范围外转人工"，现有代码里只有人工点按钮，没有策略版本、边界校验与建单失败阻断。

## 2. 定位与边界

### 2.1 它是什么

- **执行内核**：统一的操作类型目录 + 统一执行链路（第 4 章的十道门禁）+ 统一操作审计。
- **资源变更的唯一出口**：前端所有写按钮 → 调用本单元的操作接口 → 本单元判定工单/权限/前置/复核 → 经连接器落地或下发外部执行取回执。
- **资源台账的写入者**：执行结果回写资源对象状态（含部分成功、失败、待回执），保证台账与实际一致（原文 2.10-3「台账与实际状态一致」）。

### 2.2 它不是什么（明确的负向边界）

| 不做 | 归谁 | 依据 |
| --- | --- | --- |
| 出分析结论、给优化建议、判断"无需调整" | 运营分析单元（容量/成本/事件分析） | 4.3.1-3、4.4.1「**分析结果不直接授权操作**；限流、隔离、切换、重启或 Key 吊销如需执行，引用对应流程及工单」 |
| 决定批不批 | 工单/审批（含外部审批来源回写） | 1.1-7/8；专业复核 ≠ 业务审批（4.3.1-4） |
| 面板展示、指标计算 | 监控数据面板（第 5 章） | 5.1-6「面板不新增自动动作」 |
| 定义安全门禁是否达标（哈希、扫描、评测阈值） | 安全准入能力 | 2.1-3～5、5.7-3 |
| 自动放宽限制、自动升配额、自动扩权 | 禁止 | GW-12、2.8-1「运营跟踪触顶或异常调用，**不擅自提高额度**」 |
| 应用上架审批 / 使用目录 / 消费权限 | **应用中心** | 4.2 引言「模型侧负责技术注册及网关路由，应用侧负责上架审批、使用目录及消费权限」；GW-02「不开放应用中心」 |

### 2.3 与相邻单元的接口

- **工单/审批**：本单元是工单的执行侧。一个工单可承载一次「审批+执行+验证」原单闭环；独立后续变更建**关联变更单**（原文 1.1-8，边界待确认）。需要暴露给工单的能力：可执行动作枚举、入参 schema、预检结果、执行状态、验证结果、回退结果。
- **监控面板**：面板给"跳到哪张单/哪条操作"的入口（钻取），不直接调执行接口；执行的状态回流到面板（SP-08 人工自动变更与效果验证）。
- **运营分析**：分析产出建议 → 只能生成工单，不能直接调本单元；本单元把执行结果与效果验证回填给分析做偏差复盘（4.3.1-5）。
- **权限中心**：本单元每次调用必须拿到「账号有效权限 + 数据范围」，由后端二次校验（原文 1.3「不能只隐藏前端按钮」）。
- **通知中心**：过程/结果通知 + 工单入口；发送成功与送达/确认分开展示（SP-07）。
- **外部系统连接器**：见第 9 章。

### 2.4 跨域边界（已定稿 2026-11-10：应用发布归应用中心）

**结论：应用发布不是本单元的职责。** 上架审批、使用目录、消费权限、发布/灰度/回滚执行，全部归**应用中心**；本单元只负责资源侧。

本单元与应用中心的接口收敛为两件事，都不越界：

| 接口 | 谁发起 | 本单元做什么 | 本单元不做什么 |
| --- | --- | --- | --- |
| 发布前资源影响校验 | 应用中心 | 只读回答：目标应用要用的模型渠道是否健康、凭证是否有效、配额是否够、变更窗口是否冲突；返回影响面与阻塞项 | 不发起发布、不改应用状态、不代做上架审批 |
| 发布后状态交接 | 应用中心 | 接收发布结果与回执，把「模型渠道/凭证/配额」侧需要跟进的事项登记为待办或关联工单 | 不写应用的消费权限、不把技术登记写消费侧获权 |

两接口**一律走工单，不做直连调用**（2026-11-10 确认）：发布前由应用中心提一张只读的「资源影响校验单」，本单元在同一张单上回填影响面与阻塞项；发布后由应用中心提「状态交接单」，本单元在其上登记资源侧待办并回执。好处是跨域来回都有单据、都能审计，也不用两边各实现一套同步协议。

口径依据：原文 4.2 引言「模型侧负责技术注册及网关路由，应用侧负责上架审批、使用目录及消费权限」、GW-02「不开放应用中心」。**目录里仍保留 `OC-G-05` 一条，唯一作用是把边界显式化：在本单元发起会被 g0 归属边界直接拦下并指向应用中心。**

## 3. 操作目录（Operation Catalog）—— 需求主体

编号规则：`OC-<组>-<序号>`，组 = A 模型资产 / B 部署上线 / C 网关配置 / D 凭证配额 / E 算力训练 / F 运行弹性 / G 应用与MCP / H 平台配置。**共 56 条**（A8 / B6 / C5 / D9 / E10 / F7 / G5 / H6）；**本单元实为 55 条 + 1 条边界条目**（`OC-G-05` 已定归应用中心，保留只为把 g0 归属边界显式化），已同步导出为结构化清单 `operation-catalog.csv` / `operation-catalog.json`（17 字段，含 `exec_mode`、`dual_review`、`auto_allowed`、`priority`、`source_ref`，可直接进需求跟踪表；统计：执行归属 人工 24 / 平台自动 18 / 待确认 14，允许自动执行 12、否 33、待确认 11，需双人复核 5 + 建议纳入 2 + 待确认 3，优先级 P0 13 / P1 36 / P2 7）。
每条字段：**触发** ｜ **前置与硬阻断** ｜ **审批与复核** ｜ **执行归属** ｜ **成功判定** ｜ **回退**。
执行归属三值（原文 6-3 要求区分）：`人工` / `平台自动` / `外部执行需回执`；未确认能力一律标 `待确认`，不得假定可用。

### A 组 · 模型资产与准入

- **OC-A-01 发起统一模型准入工单** ｜人工（内部微调产物由用户主动申请上线触发）｜前置：来源类型×制品形态两维齐全、外部须可信来源/文件清单/声明哈希、内部须关联原训练任务+产物版本+保存哈希基准 ｜ 审批：系统管理员（岗位待确认）｜执行：人工提交｜成功：工单受理；**建单成功≠准入通过**｜回退：同单补证，不另建第二套审核单（原文 2.1-1、2.4-1）
- **OC-A-02 外网→内网传输交接登记** ｜工单内步骤｜前置：约定通道；页面上传仅接收内网文件，**不代替传输手续**；未完整读取不得进校验扫描 ｜ 人工｜成功：交接证据可追溯｜回退：列明失败地址/文件后重读（2.1-2）
- **OC-A-03 触发完整性校验 + 安全扫描** ｜工单触发｜前置：实际待准入文件可完整读取 ｜ **平台自动**（扫描能力自带/外接待确认）｜成功：哈希记录+扫描报告产出；**执行失败≠校验通过**｜回退：暂停流转，整改复验；禁止重写基准或用基座哈希替代（2.1-3）
- **OC-A-04 登记可信来源独立核实证据（三方哈希比对）** ｜工单内步骤｜前置：系统管理员**独立**在可信来源核实并留证；工单值/独立核实值/平台重算值**三者一致**才通过 ｜ 人工（系统管理员）｜成功：三方一致 + 证据可核查；官方无哈希不得伪造或直过｜回退：暂停放行要求补证（2.1-4；是否双人复核见 6-准-5）
- **OC-A-05 触发安全边界与违规输出评测** ｜工单触发｜前置：覆盖实际开放的文字/图片/音频/视频能力；内网微调不豁免 ｜ 平台自动 + 运营组织（边界待确认）｜成功：达经确认的通过要求；**报告生成≠评测通过**｜回退：整改复测；叠加防护/限期加固须另批措施·责任·期限（2.1-5、6-准-8/9）
- **OC-A-06 审批准入 + 资产登记入库（状态置「可被部署选择」）** ｜工单｜审批：系统管理员，同单汇总证据、**不另设安全签字** ｜ 系统管理员审批 + 平台自动登记｜成功：**审批通过 且 登记入库成功** 双条件；否则不得显示可部署｜回退：登记/存储转移失败同单记录重试；失败与回退同样留痕（2.1-6）
- **OC-A-07 受控存储读取/变更（权重）** ｜按需｜前置：最小权限 ｜ 平台自动 + 人工｜成功：读取/变更均有审计｜回退：不适用（只留痕）（2.1-6、2.3-5）
- **OC-A-08 例外审批：安全不达标叠加防护 / 限期加固** ｜工单｜审批：**待确认（6-4 未定谁批）**｜人工｜成功：措施+期限+验收齐备｜回退：到期未验收不得持续放行（2.1-5、6-4）

### B 组 · 部署与网关上线

- **OC-B-01 发起部署工单** ｜人工，**仅运营人员**｜前置：模型已准入且入库成功可部署；**只选模型名称**，平台关联版本+默认配置；默认配置缺失→展示缺失项，**不得临时要求运营填参数** ｜ 审批：有权限运营或系统管理员；**允许申请人自审并留痕，仅限部署工单**（2.5-2）｜执行：平台自动｜成功：见 OC-B-02｜回退：驳回不启动（2.5-1）
- **OC-B-02 自动部署并接入网关（三段成功判定）** ｜审批通过触发｜前置：可用算力、预设参数可用 ｜ **平台自动**｜成功（**必须同时满足**）：① 实例健康检查通过 ② 网关注册成功 ③ 路由生效 ④ **经网关试调用成功**；仅实例启动**不算**成功；部分成功须按状态如实展示 ｜ 回退：按已确认原工单授权/策略办理，未明确部分标待确认；执行/失败/回退全留痕（2.5-2）
- **OC-B-03 维护默认部署配置 / 预设参数** ｜管理配置变更工单｜审批：待确认（系统管理员维护）｜人工 + 平台｜成功：版本化留痕；**不变成每次部署的人工补参步骤**｜回退：版本回退（2.5-1）
- **OC-B-04 经网关试调用 / 主动探测（本身是写型验证动作）** ｜部署收尾自动 / 巡检｜前置：**方式、频率、授权、成功边界全部待确认（MS-02）**；不得虚构探测频率或真实发起检测（SP-04）｜平台自动｜成功：调用成功｜回退：失败不得显示上线成功（2.5-2、MS-02、SP-04）
- **OC-B-05 模型版本升级** ｜工单 + 批准窗口｜前置：影响与依赖清单 + 系统管理员专业评估记录 + **可用配置快照** ｜ 审批：有权限审批岗位（待确认）；**专业确认不代替执行审批**；执行限于批准对象/窗口/权限 ｜ 平台自动（**复用 OC-B-02**）｜成功：三段成功 + 依赖无残留｜回退：从快照回退并复验；**无法建立可用快照时先修复，不承诺可恢复**（2.10-1/2）
- **OC-B-06 模型下线** ｜工单 + 批准窗口｜前置：未处理依赖为 0；下线建议须关联原分析任务 + 数据依据 + 管理员确认记录，**不因建议自动下线** ｜ 同上｜人工（运营执行，MCP 岗位配合）｜成功：入口已停用 + 路由清理 + 关联授权清理 + 台账一致；**不得把局部清理写为全部下线**｜回退：按批准方案回退并复验，无法回退升级事件（2.10-2/3）

### C 组 · 网关配置（渠道 / 别名 / 协议 / 路由 / 策略）

## 4. 统一执行链路（十道门禁）

每一次写操作都走同一条链路；`OC` 编号的动作只是这条链路上的参数不同。**"必须阻断"列是本单元的可测试硬断言。**

| # | 步骤 | 必须阻断（硬断言） | 现有可复用实现 | 缺口 |
| --- | --- | --- | --- | --- |
| 0 | 归属边界 | 非本单元的动作（应用发布 / 上架审批 / 消费授权）不得在本单元发起 → 拒绝并指向应用中心 | — | **本次新增** |
| 1 | 意图与对象解析 | 目标对象不可定位 / 版本不可定位 → 拒绝 | `workflow` 提交即解析 target | — |
| 2 | **工单绑定** | 无覆盖本次「审批+执行+验证」的工单 → 拒绝执行（人或系统执行同规则） | 工单 `WO-xxxx` 体系、`trace()` | 系统自动动作的建单入口 |
| 3 | 权限项校验（**后端**） | 账号对该**操作项**无 execute/approve/review 权限 → 403；仅前端隐藏不算 | `PermKey view/manage` 判定在服务端（"改前端没用"） | 权限项只到模块级，未到操作级 |

| 6 | **双人执行复核** | 凭证类动作：执行与复核为不同账号、同一人不得兼任；**未复核不得标记发放成功/完成** | 无 | **全缺（最高优先）** |
| 7 | 变更窗口 + 执行队列 | 非紧急动作无开放窗口 → 排队位次保留；**同一时刻只允许一项实际执行** | `WindowSlot` 预约/开启/结束 + 串行队列 + `URGENT_TYPES` | 自动动作与队列的协同 |
| 8 | 执行 | 执行归属必须三选一：人工 / 平台自动 / **外部执行需回执**；未回执前不得改资源占用 | `EXTERNAL_TYPES=['model_deploy']`、`external` 状态 + 回执（回执须 ≥6 字说明） | 只有 model_deploy 走外部回执 |
| 9 | **后验证与分段成功判定** | 部署：实例健康 + 网关注册 + 路由生效 + 经网关试调用 **四者齐备**才算上线成功；扩缩容须同口径负载/时延/失败前后对比；**不以实例数变化或登记完成代替验证** | `生效验证` 步骤（粗） | 分段成功口径、效果验证器 |
| 10 | 通知 + 台账 + 回退/升级 | 通知失败不得伪称已通知；发送成功 ≠ 送达 ≠ 已接手；回退失败保持事件在途并转故障单；台账与实际一致 | 通知中心、`fallback_tasks` 人工兜底工单、`sweep_commands` 超时自动转兜底 | 送达确认判据、回退策略表 |

## 5. 操作模型与状态机

### 5.1 统一操作对象（Operation）建议字段

`operation_id`｜`operation_code`(OC-xx)｜`resource_type`｜`resource_id`｜`params`｜`ticket_id`（关联工单，必填）｜`parent_ticket_id`｜`strategy_id/version`（自动动作必填）｜`requested_by`｜`approved_by`｜`executed_by`｜`reviewed_by`（双人复核）｜`exec_mode`(人工/平台自动/外部需回执)｜`precheck_result` + `impact`｜`before_snapshot` / `after_snapshot`｜`status`｜`started_at` / `finished_at`｜`ack_at`/`ack_by`（外部或设备回执）｜`verify_result`｜`rollback_of` / `rollback_result`｜`notify_records`｜`fail_reason`｜`idempotency_key`｜`data_scope`

### 5.2 状态机（合并现有两套词表，统一为一套）

```
草稿 → 预检通过 → 待审批 → 已审批待执行 → 待复核 → 待窗口(排队) → 执行中
     → 已下发·待回执 → 已生效 → 已验证 → 已闭环
                              ↘ 失败 → 待人工兜底 →（人工接管 / 已回滚）
     已驳回（终态，可重提）
```

- 与现有映射：`submitted`→待审批，`approved`→已审批待执行，`queued`→待窗口，`external`→已下发·待回执，`closed`→已闭环，`rolled_back`→已回滚；**新增**：预检通过、待复核、待人工兜底。
- **部分成功必须可表达**：如"实例健康但网关注册失败"→ 状态 = 失败（环节=网关注册），**不得显示整体上线成功**（原文 2.5-2/3、6-2）。
- **幂等**：同一 `idempotency_key` 同一结果只生效一次（沿用 `commands` 回写幂等口径）。
- **执行锁**：同一资源对象同一时刻只允许一个实际执行中的变更（沿用"变更窗口串行"口径并扩展到对象级）。

### 5.3 快照

执行前强制留 `before_snapshot`（配置/副本/路由/配额/策略版本），下线与升级前置"可用快照"；**无法建立可用快照时先修复，不承诺可恢复**（2.10-1）。快照能力是否已有 → 待确认（6-3）。

## 6. 权限模型（对齐原文 1.2/1.3 与现有 `PermKey`）

### 6.1 建模原则

1. **三类账户角色不变**（系统管理员 / 运营人员 / 普通用户，原文禁止新增第四角色），角色只提供"可参考的能力范围"，**不把同角色账号权限绑成同一集合**。
2. **权限项 = 操作级 + 动作类型**，不是模块级。建议权限项命名：`<资源域>.<对象>.<动作>`，动作枚举 `view | request | execute | approve | review | export_raw | config`。
3. **后端强制**；前端只做可见/可用控制（原文 1.3 明写"不能只隐藏前端按钮"）。
4. **数据范围维度**：本人 / 本组织 / 本业务线 / 全局；敏感原文（请求/响应内容）**逐账号单独授权，运营或管理员角色不自动全开**（4.4.3、GW-05/14）。

### 6.2 权限项清单（建议枚举，需业务确认后定稿）

- 模型：`model.admission.request/execute/approve`、`model.asset.register`、`model.deploy.request/approve/execute`、`model.retire.request/approve/execute`、`model.preset.config`
- 网关：`gateway.route.config`、`gateway.policy.config`、`gateway.quota.config`、`gateway.failover.execute`
- 凭证配额：`key.request`（含代申请）、`key.approve`、`key.execute`、`key.review`（复核，与 execute 互斥同人）、`key.quota.adjust.request/approve/execute/review`、`key.revoke.execute`、`key.inventory`
- 算力训练：`train.apply`（对应原文示例"模型训练算力申请"）、`train.approve`、`train.allocate`、`train.extend.request/approve/execute`、`train.control.self`、`train.weight.export/cleanup`
- 弹性：`autoscale.strategy.config/approve`、`autoscale.execute.auto`（策略授权）、`scale.manual.execute`
- 应用与 MCP：`mcp.register/config/execute`、`mcp.isolate/restore.execute`、`app.publish.execute`、`app.handoff.record`
- 平台配置：`account.role.assign`、`perm.item.configure`、`alert.rule.config`、`log.policy.config`、`metric.caliber.config`、`connector.config`
- 数据：`log.query.self/org/global`、`log.content.raw`、`export.masked`、`export.raw`（**与脱敏导出权限分开**）、`audit.query`

### 6.3 四条强制策略（必须落在代码里，不能靠流程约定）

1. **双人复核策略**：`key.execute` 与 `key.review` 不可为同一账号，且发放记录必须有 `reviewed_by` 才可进入"已生效"。建议扩展到：额度调整、轮换、吊销、以及"哈希独立核实"（6-准-5 待确认）。
2. **自审白名单**：仅 `model.deploy.*` 允许 `requested_by == approved_by`，其余动作强制 `requested_by != approved_by`。
3. **紧急通道**：单独权限（现有 `security_emergency` 可参照）+ 不受变更窗口限制 + **必须事后补审与关联变更工单**（紧急处置授权机制待确认，6-1）。
4. **自动动作身份**：平台自动执行必须使用**具名系统账号**并携带 `strategy_id/version` + `ticket_id`，审计上与人工等价（原文 1.1-8"无论人或系统执行"）。

## 7. 自动执行与策略授权边界（Auto-Op）

原文对自动化的表述只给了扩缩容一个完整范式，本单元把它抽象为通用能力，其余动作按同一模型接入。

**策略对象（AutoOpPolicy）字段**：策略标识 + **版本**、适用对象范围、触发指标与口径、触发阈值 + **持续时长**（禁止用短时低负载判定）、粒度（实例数/卡数）、最小/最大规模、冷却期与防抖、请求保护与连接排空条件、算力可用性与预占校验、授权期限、生效状态（未获批/已获批/暂停）、责任运营账号（通知映射）。

**判定三态**（每次触发都必须实时判定并留痕）：

| 判定 | 行为 |
| --- | --- |
| 在获批策略范围内 | **先建变更工单 → 自动执行**，不逐次等人工审批 |
| 超出范围（越界、算力不足、无窗口、策略过期） | 转人工审批；工单标注超范围原因，**不执行** |
| 无获批策略 / 建单失败 | **硬阻断，不执行**，记录待办并升级 |

**可自动化 / 不可自动化清单（建议，需确认）**

- 可自动化：推理副本扩缩容（F-01）、训练到期停止与算力回收（E-08）、到期权重清理（E-10，须原工单已定策略）、异常 MCP 服务移出路由（G-03，边界待确认）、Key 到期提醒与凭证盘点（D-07）、健康探针自愈与 fallback 切换（C-04，顺序待确认）。
- **不得自动化（默认人工审批）**：任何放宽配额/限额/权限的动作（GW-12、2.8-1）、Key 生成与吊销（双人复核）、模型下线（2.10）、权限项开关（1.3）、策略与阈值配置本身（1.1-9、6-5）、日志留存与删除（4.4.3）。
- 大模型辅助生成的建议**不是执行授权**：确定性阈值与实时扩缩按既定机制执行，"不交大模型随意判定"（1.1-14）。

## 8. 审计与留痕

### 8.1 统一操作审计三段式（每条操作都必须齐）

- **意图段**：操作码、目标对象与版本、关联工单（申请人/对象/变更前后内容）、请求账号与数据范围、参数。
- **执行段**：审批人与审批结论、执行人、复核人（凭证类）、执行归属与外部回执（`ack_at/ack_by`）、开始/结束时间、快照（前后资源/副本/路由/配置/策略版本）、每一步状态。
- **结果段**：最终结果（含部分成功与失败环节）、**效果验证证据**（同口径负载/时延/失败对比）、回退结果、通知记录（尝试/发送/送达/失败分列）、未闭环事项与责任人。

### 8.2 与其他审计的边界（原文强制分开）

- **管理变更审计**（谁改了什么配置）**≠ 查询/导出审计**（谁查了/导了什么）：两者"采集和关联分别评估"，不能互相代替（GW-14）。
- 不逐次建单的正常操作（查询、面板、逐请求推理、按批准策略分流、授权内训练操作、到期回收）**仍保留运行/操作审计日志**（1.1-10/11）。
- 任务内导出是原任务证据，**导出权限与审计仍保留**；**原文与摘要导出权限分开**；导出含未授权敏感数据 → 停止交付并记录（4.4.2-2）。
- Key 一律以**哈希脱敏**形式出现，不记录可用明文凭证（GW-02）。
- 敏感原文（请求/响应内容）：逐账号授权、访问留审计、缺失/关闭/截断必须如实标识、不伪造零用量（4.4.3、GW-05/14）。
- 权重到期清理**不删除全部追溯与审计记录**（1.1-11）。
- 日志与审计字段建议对齐现有 `events` / `fallback_tasks` / `commands` 表，并新增 `operations` / `operation_steps` / `snapshots` 三张表（`server/schema.sql`）。

## 9. 外部系统对接（Connector）要求

| 方法 | 要求 |

## 11. 分期落地

- **P0（先立骨架，1 个迭代）**：统一操作模型与状态机、操作目录（先实现 D 组 + B-01/02 + E-04 + G-03 四类代表动作）、十道门禁内核（工单绑定、后端权限项、预检强制、双人复核、无单不执行）、操作审计三段式落库。

- **P2**：MCP 自动隔离、策略/阈值版本化配置中心、灰度发布（若业务定义；**模型流量灰度属本单元，应用发布灰度归应用中心**）。
- **不做**：应用发布与上架（2026-11-10 确认归应用中心，见 2.4）；本单元只提供发布前只读资源校验与发布后状态交接两个接口。

**验收硬断言（可直接写测试）**

1. 无 `ticket_id` 的写请求 100% 被拒，且被拒事件留审计。
2. `key.execute` 与 `key.review` 同人 → 拒绝；无 `reviewed_by` 的 Key 记录不得为"已生效"。
3. 未做 dry-run 的指令下发 → 拒绝（现有行为，保留为回归用例）。
4. 部署只完成实例健康 → 界面与 API 均不得返回"上线成功"。
5. 扩缩容触发时若策略未获批或建单失败 → 无任何资源变化，且生成待办与升级通知。
6. 请求参数中把配额调高但工单审批值更低 → 以审批值执行或拒绝，绝不取参数值。
7. 部分成功场景（如路由生效但试调用失败）→ 状态与失败环节如实展示，台账不回滚为"未部署"。
8. 连接器不可用 → 明确"读不到"，不使用默认假数据，不显示成功。
9. 紧急通道操作 → 必须带 `security_emergency` 类权限，且生成事后补审待办与关联变更单。
10. 导出含未脱敏敏感原文 → 停止交付并记录原因。
11. 前端隐藏按钮但直调接口 → 后端 403（权限校验在服务端）。
12. 同一幂等键的回执重复回写 → 只生效一次。
